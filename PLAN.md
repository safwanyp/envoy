# Envoy — plan

> Many agents, one main branch. The radar prevents most conflicts; replay regenerates the rest.

Entry for the Cloudflare "next Git platform" competition
(https://blog.cloudflare.com/next-git-platform-on-cloudflare/).
**Deadline: Oct 14, 2026.** Submission = 5–10 min video + MIT source + run instructions.

---

## 1. The idea

Today's Git merges **text**. When two agents edit the same thing, someone has to fix the conflict by hand.
Envoy treats a change as **intent + diff**, not just diff. That gives us two capabilities:

1. **Conflict radar (prevention).** Before an agent edits code, it claims the files/symbols it plans to touch.
   A per-project coordinator tells it, in real time, who else is touching them and *why* ("agent-3 is
   rewriting `validateLogin()` to add rate limiting"). The agent can yield, narrow scope, or go ahead.
2. **Replay merge (resolution).** If a landing still conflicts, Envoy does not ask anyone to resolve
   conflict markers. It discards the stale diff, forks the *current* main, and re-runs the agent's
   **intent** there. The replayed agent is told what landed in the meantime and why, using the intent
   trailers on main's commits.

Every commit on main carries its intent, so `git log` answers *why*, not just *what*.

The pitch for the video: run 6 agents on overlapping tasks against one repo. Main never contains a
conflict marker, nobody resolves anything by hand, and every commit explains itself.

### Explicit non-goals (3-day scope)
- No accounts, orgs, permissions, issues, or a GitHub-like web UI.
- No multi-language symbol parsing. The demo repo is JS, and symbols are extracted with a small
  JS-only extractor.
- No running the target repo's tests in v1 (see stretch: Worker Loader / Sandbox).

## 2. Stack & conventions

- **Runtime code is plain JS (ESM).** No `.ts` source files.
- **Types live in colocated `.d.ts` files** (e.g. `src/coordinator/types.d.ts`). JS files reference
  them via JSDoc: `/** @typedef {import('./types').Claim} Claim */`, `@param`, `@returns`, `@type`.
- **`tsc --noEmit`** enforces types (`allowJs`, `checkJs`, `strict`). `pnpm typecheck` must pass before
  anything is called done.
- Binding/runtime types are generated by `cf workers types` → `.cloudflare/types/index.d.ts`. That file
  is the source of truth for `Env`, `Artifacts`, `DurableObjectNamespace`, etc. Regenerate it after any
  change to `cloudflare.config.ts`.
- Factory functions and plain objects over classes, except where the platform requires a class
  (Durable Objects, `WorkerEntrypoint`).
- Pure logic (radar overlap, trailer parsing, symbol extraction, merge classification) lives in modules
  with no I/O and is tested with `node --test`.
- Few dependencies: `isomorphic-git` (required), `cf`, `vite`, `@cloudflare/vite-plugin`, `typescript`.
  No framework router. The UI is vanilla JS + web components served as Workers static assets.
- Package manager: pnpm. Use the **`cf` CLI** (not Wrangler) for types, local dev, and deploy.

## 3. Architecture

```
                 ┌──────────────────────── envoy Worker ────────────────────────┐
  UI (static) ──►│ fetch router  ── /api/*  ──►  Coordinator DO (1 per project)   │
  WebSocket   ◄──│                              • agents registry               │
                 │                              • claims / radar (SQLite)       │
                 │                              • landing queue (serialized)    │
                 │                              • intent log, replay lineage    │
                 │                              • WS broadcast to UI            │
                 │                                   ▲          │ spawn/replay  │
                 │                                   │ claim    ▼               │
                 │                              AgentRunner DO (1 per attempt)  │
                 │                              • fork main (Artifacts binding) │
                 │                              • clone → MemoryFS (iso-git)    │
                 │                              • LLM tool loop                 │
                 │                              • commit w/ intent → push fork  │
                 │                                                               │
                 │ queue consumer ◄── Queue ◄── Artifacts event subscription     │
                 │   (main repo `pushed` events → Coordinator.onMainMoved)      │
                 └──────────────────────────────────────────────────────────────┘
                         Artifacts: <project>-main, <project>-a-<attemptId> forks
```

### Components

**`src/index.js`.** Worker entry. It routes `/api/*` to the Coordinator (a DO stub by project ID),
serves static assets, runs the queue consumer, and exports the DO classes.

**Coordinator DO (`src/coordinator/`).** One per project, using the SQLite storage backend. Owns:
- `agents`: attemptId, taskId, intent, status (`planning|editing|yielding|landing|landed|replaying|failed`),
  forkName, baseCommit, replayOf, replayCount.
- `claims`: attemptId, path, symbol|null, kind (`declared|actual`), createdAt.
- `landings`: serialized landing queue. Only one landing runs at a time (in-memory promise chain plus a
  SQLite row so the queue survives DO restarts).
- `intents`: commit sha on main → intent record. Mirrored from trailers so the UI can query it.
- WebSocket hub (hibernatable WebSockets API) that pushes every state change to the UI.

**AgentRunner DO (`src/agent/`).** One per *attempt* (a replay is a new attempt linked by `replayOf`). Steps:
1. Fork main using `env.ARTIFACTS.get(main).fork(name)` and record `baseCommit`.
2. Clone the fork into `MemoryFS` with isomorphic-git (the demo repo is tiny).
3. **Plan step.** The LLM returns `{ summary, claims: [{ path, symbol? }] }` and the plan's claims are
   sent to the Coordinator via `claim()`.
4. The radar answers with `clear` or `overlap` (with the other agents' intents). A deterministic policy
   (not the LLM) decides what happens:
   - Same symbol, other agent started earlier → **yield**. Wait for the other agent to land, then
     re-fork from the new main and continue. This is cheap and needs no replay.
   - Same file, different symbol → **proceed** (it will most likely merge cleanly). Show a warning in the UI.
5. **Edit loop.** Tools: `list_files`, `read_file`, `write_file`, `claim`, `finish`. A `write_file` to an
   unclaimed path auto-claims it and runs a radar check.
6. Commit with intent trailers (and the intent file, see §4), push to the fork, then call `requestLanding()`.

**Landing (`src/git/land.js`, run by the Coordinator's queue).**
1. Fetch main and the attempt's fork into one MemoryFS.
2. If main's head == baseCommit → fast-forward push.
3. Otherwise run isomorphic-git `merge` with `abortOnConflict: true`:
   - clean → push the merge commit to main (trailers preserved on the agent commit).
   - conflict → **replay**: mark the attempt `replaying` and spawn a new AgentRunner with the same intent
     plus a replay context (§5).
4. Fallback if iso-git merge misbehaves: do a file-level 3-way. If the files the agent changed since
   base are disjoint from the files main changed since base, overlay them; otherwise replay.
5. Push events report the result back via the main repo's event subscription.

**Main-moved handler (`src/events/artifacts.js`).** A queue consumer for `cf.artifacts.repo.pushed` on
the main repo. It calls `Coordinator.onMainMoved(after)`, which diffs the landed commit's
files/symbols against in-flight agents' claims. If an in-flight agent's claims were invalidated,
it gets a **stale** signal and replays *early*, before it wastes time finishing a doomed diff. This
proactive replay is the strongest beat in the demo.

> Pushed events are **repo-level** subscriptions. We only subscribe the main repo (one subscription,
> created by `scripts/subscribe.js`). Fork pushes are reported directly by the AgentRunner, so we don't
> have to create a subscription per fork.

**LLM (`src/agent/llm.js`).** A thin client behind one function, `complete({ system, messages, tools })`.
Default: a tool-calling Workers AI model via the `AI` binding (zero keys). It can be swapped to
Anthropic/OpenAI through AI Gateway with one env var. Pick the model on day 1 by testing tool-call
reliability.

**UI (`public/`).** Vanilla JS + web components, connected over WebSocket. Three panels:
- **Radar:** rows = files, sub-rows = symbols, colored chips = agents with claims. Overlaps glow, and
  yields/stale signals animate.
- **Main timeline:** commits on main with their intent text, agent, and a "replayed ×N" badge.
- **Lineage:** per task, the chain of attempts (attempt 1 → conflict → attempt 2 landed), with the
  stale diff vs. the landed diff.
Plus a "Run demo" button that loads `demo/tasks.json`.

## 4. Intent format

Every agent commit message:
```
<one-line summary>

<short rationale from the plan step>

Envoy-Task: t_rate_limit
Envoy-Attempt: a_7f3c
Envoy-Agent: agent-3
Envoy-Intent: Add per-IP rate limiting to POST /login (5/min)
Envoy-Claims: src/routes/auth.js#validateLogin, src/lib/limiter.js
Envoy-Replay-Of: a_19b2            # only on replays
Envoy-Base: <sha>
```
The full intent record (task prompt, plan, claims, replay context summary) is also written to
`.envoy/intents/<attemptId>.json` in the same commit. Paths are unique, so these files never conflict.
That puts the *why* inside the repo itself, and any git client can see it.

`src/git/intent.js` is a pure module: `formatTrailers(intent)` / `parseTrailers(message)`, with tests.

## 5. Replay context

When an attempt is replayed, the new AgentRunner receives:
- the original task prompt + intent,
- **what landed since its base**: the list of `{ sha, agent, intent, changed paths/symbols }` read from
  trailers on main between `baseCommit` and the current head,
- its own previous (stale) diff, labeled "reference only, do not apply blindly".

System prompt framing: "Main moved underneath you for these reasons. Re-implement your intent on top
of the current code, and respect what those changes were trying to do." `maxReplays = 2`. After that,
the attempt is marked `needs-human` and shown in red in the UI. (That's fine to show once in the demo.)

## 6. Radar logic (pure, `src/coordinator/radar.js`)

- `Claim = { attemptId, path, symbol: string | null, kind: 'declared' | 'actual' }`
- `findOverlaps(claims, incoming) → Overlap[]` where `Overlap.level` is `'symbol' | 'file'`.
  A `null` symbol means the whole file, so it overlaps every symbol in that file.
- `decide(overlap, self, other) → 'yield' | 'proceed'`: yield on a symbol-level overlap when the other
  agent started earlier; proceed otherwise.
- `staleAfterLanding(landedChanges, inFlightClaims) → attemptId[]`.

Symbols (`src/git/symbols.js`, pure): extract top-level `function name`, `export function name`,
`const name = (…) =>`, and `class Name` with line ranges from JS source. `changedSymbols(before, after)`
maps a file change to the touched symbols. Regex/line based is fine; the demo repo is written to match.

## 8. Demo scenario (`demo/tasks.json`)

The seed repo is a tiny API with `src/routes/auth.js` (`validateLogin`, `login`, `signup`),
`src/routes/todos.js`, `src/lib/db.js`, `src/server.js`.

| # | Task | Designed to… |
|---|------|--------------|
| 1 | Add per-IP rate limiting to login | conflict with #2 on `validateLogin` |
| 2 | Add stricter input validation to login | → **radar yield** (starts after #1) |
| 3 | Rename user field `email` → `emailAddress` everywhere | lands first, **invalidates** #1 → **proactive replay** |
| 4 | Add `GET /health` | same file as #5, different symbol → **clean merge** |
| 5 | Add request logging in `server.js` | same as above |
| 6 | Add pagination to `GET /todos` | independent, lands immediately |

Video beats: radar lights up → #2 yields → #3 lands → #1 gets a stale signal and replays with "email was
renamed because…" → everything lands → `git log` on main shows intent trailers → clone main with plain
`git` to prove it's real Git.

## 10. Risks

| Risk | Mitigation |
|------|-----------|
| Artifacts beta quirks (fork latency, `status: forking`) | Poll `info()`/`list()` until `ready`. Spike on day 1. |
| iso-git merge edge cases | File-level 3-way fallback (§3), and replay covers the rest. |
| LLM tool-calling flakiness | Deterministic radar policy, retries, small repo, tight prompts, model chosen in Spike D. |
| DO memory/CPU with in-memory clones | Tiny demo repo. One clone per attempt. Don't keep the FS between requests. |
| Event delivery latency | Coordinator also learns about landings directly. Events only drive proactive replay and the UI feed. |
| Video eats day 3 | Script the video beats on day 2 evening. Record by Wed morning at the latest. |
